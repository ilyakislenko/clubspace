# ClubSpace security audit (2026-11-01)

> Snapshot of `main` at #387, before the fixes merged in #388–#400+. Code was read, no exploit was run; `[INFERENCE]` marks reasoning rather than observation. What changed since: `docs/strategy/concept.md`.

## Summary of critical/high items
- **C1 (Critical): any coach can read and delete any other club's videos.** The checks on the `admin/videos` routes look for the club ID in the request body before the URL query. The handlers for the list, view and delete routes use the club ID from the query. A coach of club A sends club A's ID in the body and the victim club's ID in the query. The access checks pass against club A, while the handler lists, reads or deletes club B's videos. The likeliest attacker is someone who coaches in one club and trains in another, which is exactly the multi-club case.
- **H1 (High): any coach can delete arbitrary files in shared storage, across clubs.** When a subtitle is created, the server stores whatever file path (`storageKey`) the client sends. Deleting or replacing that subtitle then deletes that path from the bucket. A coach can delete other clubs' source videos (`raw/<id>/source.mp4`) or HLS playlists (`hls/<id>/...`).
- **H2 (High): refresh tokens work as access tokens, and logout doesn't end sessions.** Both token types are signed with the same secret, issuer and audience, and nothing tells them apart. The access check never looks at revocation. So a 30-day refresh token keeps working as a login token after logout, after refresh rotation, and after an admin changes the user's email.
- **H3 (High, compliance): personal-data consent is never recorded.** The server, admin and mobile code have no consent capture at all. Sentry is enabled when a DSN is set, and the place where data is stored is not tied to Russia. This blocks a lawful Russian launch under 152-ФЗ. Minors (kids' BJJ) are not handled either.

## Details

### C1: club ID mismatch between access checks and handlers on `admin/videos`
- `AuthGuard` resolves the role from `decodedToken.workspaceId || req.params.workspaceId || req.body?.workspaceId || req.query?.workspaceId` (auth.guard.ts:76-83). `WorkspaceMemberGuard` uses `params ?? body ?? query` (workspace-member.guard.ts:25-28).
- For `admin/videos/*` there is no `:workspaceId` in the path. List, get and delete build their feature from `@Query()` (`ListVideosFeatureInputSchema.workspaceId`, `GetVideoFeatureInputSchema.workspaceId`, `DeleteVideoFeatureInputSchema.workspaceId`). The service then filters by that query club ID (`video.service.ts:156-160, 190-204, 860-895`), so the filter itself is right, but it uses the club ID the guards never checked.
- Prerequisite: the attacker is coach, head coach or admin in any club A. To learn club B's ID: the join flow by code (codes are printed on posters), or being a student in B.
- Impact: lists B's whole library, reads detail (raw and HLS keys), deletes B's videos. Each deletion also removes the raw object and the whole HLS prefix.
- Fix (preferred): move these routes under `workspaces/:workspaceId/videos` and remove the body/query fallback from the guards entirely. The route-tier spec in `shared/access/route-tier-consistency.spec.ts` can enforce "every `@Roles` route has `:workspaceId` in its path".

### H1: subtitle `storageKey` used for deletes
The upload-URL endpoint returns `key`, the client sends it back in `create`, and the server trusts it. Replacing a track or `DELETE …/subtitles/:id` calls `filesService.deleteObject({ key: storageKey })` with no prefix check. That deletes any key in the single shared bucket, including other clubs' `raw/` and `hls/` objects. HLS prefixes are deterministic: `hls/${videoId}` in `apps/video-worker/src/main.ts:103`. Fix: save a server-side pending upload (`videoId`, `language`, `key`) and accept only its ID, or assert `storageKey.startsWith(\`subtitles/${videoId}/${language}/\`)` at create time and before every delete.

### H2: token type confusion and revocation
`generateStoredToken` signs `{}` plus `jti` with the same secret, issuer, audience and algorithm as the access token. `AuthGuard` → `verifyToken` accepts it, so a refresh token is a valid 30-day access token. `sign-out`, refresh rotation and the email-change cleanup only touch `RefreshToken` rows, which AuthGuard never reads. Fix: add a `typ` claim and check it everywhere. `verifyStoredToken` should also require `typ==='refresh'`. Consider a per-user `sessionVersion` so that removal, block and email change take effect immediately.

### H3: compliance
- There's no record of consent to personal-data processing (152-ФЗ art. 9) and no separate consent for minors.
- Sentry has no PII scrubbing configured.
- There's no subject-access export (M12).
- Account deletion exists (`users.service.ts` `deleteAccount`, `DELETE /me`), which satisfies App Store 5.1.1(v). But it doesn't re-authenticate (any valid access token can delete the account) and it keeps attendance and payment rows by userId. Keeping those as de-identified rows is acceptable.

### M2: video worker hardening
The ffmpeg argument list is passed without a shell (`spawn(binary, args)`), so there is no command injection. Content-type `video/*` is only declared by the client, never checked against the bytes. Add an `ffprobe -show_format` step with a container allow-list and the `-protocol_whitelist file,pipe` flag. Run the worker without network access to Postgres: today the worker writes `video.update` directly, so move that through the server via the ready queue.

### Positives observed (no action)
- Every `workspaces/:workspaceId` controller uses `AuthGuard + WorkspaceMemberGuard + RoleGuard`, and a static spec enforces route tiers.
- Handlers consistently use `findFirst({ id, workspaceId })`.
- Coach scoping goes through `RbacService`.
- OTPs: 6 digits from `crypto.randomInt`, bcrypt-hashed, 15-min TTL, attempts counted atomically, and the lockout isn't reset when a new code is issued.
- Production fails to start with weak or duplicate JWT and playback secrets, or with wildcard CORS.
- The bucket is private, with public read only on the `thumbnails/`, `subtitles/` and `playlists/` prefixes; segments are served through a membership-checked manifest proxy that allows only paths under the video's own HLS prefix.
- CSV exports neutralise spreadsheet formulas; email templates HTML-escape values; 5xx responses are generic in production.
- Containers: the server and admin images run as `node`; Postgres and Redis aren't exposed in prod; Caddy sets HSTS, nosniff and frame-deny.
- The mobile app keeps tokens in SecureStore. Secret scanning found no committed keys, and `.env` / `.env.production` are gitignored.
- Locked Next.js 16.0.11 is past the December 2025 React Server Components RCE fix (16.0.7).

### Suggested checks once fixes land
- C1: e2e tests sending a body `workspaceId` that conflicts with the query.
- H1: test that a `storageKey` outside `subtitles/<videoId>/` is rejected.
- H2: unit tests that a refresh token is rejected by AuthGuard and the realtime gateway.
- Run `scripts/verify.sh` and `route-tier-consistency.spec.ts`.
