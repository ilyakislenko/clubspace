# ClubSpace scalability & reliability audit (2026-11-01)

> Snapshot of `main` at #387, before the fixes merged in #388–#400+. Read-only review. What changed since: `docs/strategy/concept.md`.

**Summary:** the API is close to stateless and the code is careful in many places: deduplication through `NotificationDispatchLog`, joins that are safe under a race, a verified nightly backup, `/readyz` probes and Sentry. Scale and reliability break in three places, roughly in this order:
1. **The 60-second scheduler tick scans every club on every run.** Reminders, inactivity nudges, expiry warnings and push delivery all run in one serial job, and push delivery is capped at 200 notifications per minute for the whole platform.
2. **Multi-replica gaps.** Websocket events, rate limits and the scheduler tick (whose 60-second runs can overlap) aren't coordinated across replicas.
3. **Class packs can be charged twice** when a coach marks attendance while the member checks in at the same time.

Video is built for a single home server: one transcode at a time, a 720p cap, raw sources kept forever, and segment URLs signed per request so a CDN can't cache them. There are no per-club quotas, no per-club export or region support, no metrics, and schema changes go through `prisma db push` on startup.

## Architecture as it stands
Caddy → one NestJS API process. That process serves HTTP and socket.io, and also runs the BullMQ `schedule-tick` repeatable job, which does reminders, first-visit checks, payments, the retention digest and push delivery, plus the `video-ready` consumer. Notifications are written as `Notification` rows and swept by the tick to Expo. A separate `video-worker` (BullMQ `video-transcode`, concurrency 1) does S3 → ffmpeg → S3 HLS. Playback goes through the API's manifest proxy, which presigns MinIO segment URLs. Postgres, Redis and MinIO are single containers on the same host. Nightly `pg_dump` and `mc mirror` run to a host directory.

## Target architecture for 10k clubs
- **Edge:** a CDN or WAF (CloudFront/Bunny, or Yandex Cloud CDN for Russia) in front of `app`/`admin` static files (Expo web and Next.js) and the video storage. Use signed cookies or token auth per `hls/<videoId>/*` prefix; manifests become static objects.
- **API tier:** stateless NestJS pods behind a load balancer (k8s or Nomad, 3+ pods), autoscaled on CPU and p95 latency. Websockets use the socket.io Redis adapter, with no sticky sessions needed since transport is websocket-only. Rate limiting is stored in Redis. Membership and feature flags are cached in Redis (30–60 s TTL) so `WorkspaceMemberGuard` stops making two queries per request.
- **Worker tier** (separate deployments, same image, `ROLE=worker`): queues `push` (batched by 100 and rate-limited), `email` (OTP with retries), `reminders` (delayed jobs per occurrence, created a rolling 48 h ahead by a per-club `materialize` job), `daily-per-club` (inactivity, expiry, payments, digest, sharded by `workspaceId` and run at club-local time), `realtime-fanout` (coalesced invalidations) and `transcode` (GPU or CPU pool autoscaled on queue depth, with per-club concurrency caps). Failed jobs are kept, and Bull Board or a similar dashboard sits behind admin auth.
- **Data:** managed Postgres 16 with HA, point-in-time recovery and a read replica (stats, leaderboards, exports), behind PgBouncer. Migrations come from `prisma migrate deploy` run as a release job. RLS policies on `workspace_id`. Monthly partitions for `AttendanceRecord`, `Notification`, `AuditEvent` and the dispatch log, with a retention policy. Denormalized counters on `WorkspaceMember` (`lastAttendedAt`, `totalCheckIns`, `streakWeeks`).
- **Redis:** a managed HA instance or Sentinel with `noeviction`. Keep queues separate from cache (two instances), so a cache stampede can't evict jobs.
- **Object storage:** S3-compatible, one bucket per region, keys `ws/<workspaceId>/…`. Lifecycle rules: raw sources go to cold storage after transcode, orphaned `uploading` objects are removed. Storage usage is tracked per club for plan quotas and billing.
- **Regions:** fully separate stacks for RU (Yandex Cloud or Selectel, for 152-FZ) and EU/US (AWS or Hetzner plus a CDN). A small global directory (`email → regions`, `joinCode → region`) lets one app binary find a person's clubs across regions. That also covers a member who belongs to clubs in several regions or in several clubs: the workspace switcher queries the directory, then each regional API.
- **Self-hosted vs SaaS:** keep the docker-compose single-host profile as the self-hosted edition (SQLite-free, same code). The SaaS profile switches on via env: Redis-backed adapters, external S3 and CDN, worker role split, and region ID. One codebase, chosen by configuration, never two code paths in handlers.
- **Observability:** OpenTelemetry traces and metrics to Grafana (Tempo, Prometheus, Loki) or a hosted service. Service-level objectives: API p95 under 300 ms, push lag p95 under 60 s, reminder on time within 2 min, transcode wait under 15 min. Sentry for API, worker and mobile. Alerting through PagerDuty or a Telegram bot.
- **Rough capacity check** at 10k clubs × 100 members = 1M members, with about 300k slot occurrences per day: about 6M reminder pushes per day ≈ 70/s on average and about 1,500/s at the evening peak. That is easily handled by about 4 push workers sending 100-message Expo/FCM batches. About 10M attendance rows per month on one partitioned table is fine for a single Postgres primary.
