# Публикация в магазинах приложений

Как ClubSpace попадает к ученикам: одно нейтральное приложение «ClubSpace» во
всех магазинах, брендовые приложения клубов — отдельной услугой из аккаунтов
самих клубов, PWA — как запасной путь. Здесь же правила магазинов, которые
определяют эту схему, настройка аккаунта для проверки и чек-лист релиза.

Правила магазинов меняются; ссылки на первоисточники — в конце документа.
Пометка `[ВЫВОД]` означает нашу интерпретацию, а не цитату из правил.

**Подача в магазины** — тексты карточек, Data safety / App Privacy, возрастной
рейтинг, заметки для проверки, скриншоты и пошаговые чек-листы Google Play,
App Store и RuStore — в [`docs/store/`](store/README.md).

## 1. Схема распространения

| Что | Кто публикует | Идентификатор | Профили EAS |
|---|---|---|---|
| **ClubSpace** — нейтральное приложение, выбор клуба по коду, ссылке, QR | ClubSpace, наши аккаунты разработчика | `com.clubspace.app`, схема `clubspace://` | `preview`, `production` (APK), `store` (AAB / App Store) |
| **Брендовое приложение клуба** — тот же код, клуб «зашит» внутрь | Клуб, из своего аккаунта разработчика | свой (`ru.myclub.app`), своя схема | `branded` (APK), `branded-store` (AAB / App Store) |
| **PWA** — то же приложение в браузере, ставится на домашний экран | ClubSpace (или владелец инсталляции) на `app.<домен>` | — | `npm run build:pwa` |

Почему так:

- **Apple 4.2.6.** Приложения из коммерческого шаблона отклоняются, если их
  подаёт не владелец контента. Разрешённая альтернатива — «единый бинарник со
  всеми клиентами в модели агрегатора или picker». Нейтральный ClubSpace —
  именно такой picker; брендовое приложение законно, только если его подаёт сам
  клуб из своего аккаунта. Так же устроены Mindbody, Glofox, PushPress, Wodify,
  Mariana Tek.
- **Apple 4.3(a).** Не плодить Bundle ID одного и того же приложения «для разных
  городов, команд, университетов» — Apple прямо советует одно приложение.
- **RuStore §4.6** запрещает «множественные публикации одного и того же
  приложения» с минимальными отличиями. Массовые клоны из одного аккаунта —
  риск модерации.
- Член нескольких клубов (BJJ + йога + зал) ставит одно приложение и
  переключается между клубами, а не держит три.

Что видит ученик: ставит ClubSpace, входит по коду из письма, открывает
ссылку или QR клуба — и клуб появляется в приложении. Брендовое приложение
клуба работает с тем же аккаунтом: тот же e-mail открывает те же клубы в обоих.

## 2. Нейтральное приложение ClubSpace

Конфигурация — `apps/mobile/app.config.js` → `src/app-variant.js`; статического
`app.json` больше нет.

- Название «ClubSpace», Bundle ID и Android package `com.clubspace.app`,
  URL-схема `clubspace`, иконки из `apps/mobile/assets/images/`.
- Slug EAS остаётся `grappling-academy-mobile`: под ним в EAS лежат keystore
  Android и счётчик версий. Переименование создаст новый проект EAS с новым
  keystore — уже установленные приложения не смогут обновиться.
- `EXPO_PUBLIC_CLUB_PICKER=true`, `EXPO_PUBLIC_BRAND=clubspace`, клуб не зашит.
  Значения API, веб-адреса и почты поддержки записывает
  `scripts/set-mobile-target.sh --domain <домен> --support-email <почта>`.
- Переменные брендовой сборки (`EXPO_PUBLIC_APP_NAME`, `EXPO_PUBLIC_BUNDLE_ID`,
  `APP_ASSETS_DIR` …) в этом режиме игнорируются — случайно «перекрасить»
  каноническую карточку магазина нельзя.

### Ссылки `https://app.<домен>/join/<код>`

Приложение заявляет `applinks:<хост EXPO_PUBLIC_WEB_URL>` (iOS) и intent-filter
`https://<хост>/join/*` с `autoVerify` (Android). Чтобы ссылка открывала
приложение, а не браузер, веб-сервер `app.<домен>` (`apps/client`) отдаёт
`/.well-known/apple-app-site-association` и `/.well-known/assetlinks.json` из
переменных окружения контейнера `client`:

- `APPLE_TEAM_ID` — Team ID аккаунта Apple;
- `IOS_BUNDLE_ID` — через запятую, например `com.clubspace.app`;
- `ANDROID_PACKAGE` — через запятую, например `com.clubspace.app`;
- `ANDROID_CERT_SHA256` — отпечатки SHA-256 через запятую: ключ подписи
  приложения из Play Console и ключ EAS (для APK вне магазина).

Пока подтверждения нет, ссылка открывает PWA — вступить в клуб можно и там.
Кнопки магазинов на страницах `/join` и `/download` («Скачать приложение») и в
письмах берутся из `APP_STORE_URL`, `PLAY_STORE_URL`, `RUSTORE_URL`. Пока
приложения нет ни в Google Play, ни в RuStore, Android-кнопка — «Скачать для
Android» по прямой ссылке `ANDROID_APK_URL` (APK можно положить в бакет под
`downloads/`, его читают без подписи); без App Store `/download` показывает
для iPhone, как добавить PWA (`PWA_URL`) на экран «Домой».

## 3. Брендовое приложение клуба (платная услуга)

Тот же код с зашитым клубом. Публикуется **только из аккаунтов разработчика
клуба** — иначе 4.2.6/4.3(a) в App Store и §4.6 в RuStore.

### Процесс

1. **Клуб заводит аккаунты** (на юрлицо или ИП клуба):
   - Apple Developer Program (организация, D-U-N-S), добавляет ClubSpace в
     команду App Store Connect с ролью App Manager или Developer;
   - Google Play Console, приглашает ClubSpace пользователем с правами на
     релизы;
   - RuStore Консоль (VK ID, юрлицо / ИП / самозанятый), добавляет ClubSpace
     в команду.
2. **Проект EAS для клуба.** Отдельный проект Expo (в организации клуба или в
   нашей, с доступом клуба). В нём — переменные окружения среды `production`
   (`eas env:create --environment production …`); их читают профили
   `branded` / `branded-store`:

   | Переменная | Обяз. | Что это |
   |---|---|---|
   | `EXPO_PUBLIC_APP_NAME` | да | Название на иконке и в магазине, оно же заголовок экрана входа |
   | `EXPO_PUBLIC_BUNDLE_ID` | да | Bundle ID / package клуба, например `ru.kimura.app`; **не** `com.clubspace.*` |
   | `APP_ASSETS_DIR` | да | Папка (относительно `apps/mobile`) с `icon.png`, `adaptive-icon.png`, `splash-icon.png`, `favicon.png` — свои, не иконка ClubSpace |
   | `EXPO_PUBLIC_WORKSPACE_KEY` | да | Ключ клуба из `/platform` |
   | `EXPO_PUBLIC_BRAND` | да | Пресет текстов и цвета: `grappling`, `fitness`, `yoga`, `clubspace`, `custom` |
   | `EXPO_PUBLIC_API_URL`, `EXPO_PUBLIC_WEB_URL`, `EXPO_PUBLIC_SUPPORT_EMAIL` | да | Сервер, веб-адрес (юридические страницы, ссылки), почта поддержки |
   | `EAS_PROJECT_ID` | для push | ID этого проекта EAS |
   | `GOOGLE_SERVICES_FILE` | для push на Android | `google-services.json` проекта Firebase клуба (файловая переменная EAS) |
   | `EXPO_PUBLIC_APP_COLOR` | нет | `#rrggbb` — цвет уведомлений и темы PWA |
   | `EXPO_PUBLIC_APP_SCHEME` | нет | URL-схема; по умолчанию Bundle ID строчными |
   | `EXPO_PUBLIC_APP_SLUG` | нет | Slug проекта EAS; по умолчанию Bundle ID через дефисы |

   В `eas.json` этих значений нет намеренно: значения из `eas.json` перекрывают
   переменные EAS.
3. **Сборка и отправка:**

   ```bash
   cd apps/mobile
   npx eas build --profile branded-store --platform all
   npx eas submit --profile branded-store --platform android
   npx eas submit --profile branded-store --platform ios
   ```

   Сертификаты iOS и APNs-ключ создаются в команде Apple клуба
   (`npx eas credentials`). Первую загрузку в Play делают вручную.
4. **Ссылки.** Брендовое приложение заявляет `/join/*` на хосте своего
   `EXPO_PUBLIC_WEB_URL`. На общем хосте платформы в `.well-known` указывайте
   только ClubSpace: `APPLE_TEAM_ID` там один, а Team ID у клуба свой.
   Брендовому приложению нужен собственный хост (своя инсталляция или домен
   клуба).

`scripts/check-release-env.mjs` отказывается собирать брендовый профиль без
названия, Bundle ID, ключа клуба или иконок, с Bundle ID `com.clubspace.*`, с
иконкой ClubSpace, со схемой `clubspace` или с `EXPO_PUBLIC_CLUB_PICKER=true`.

## 4. Правила магазинов, которые нас касаются

### Apple App Store

- **3.1.1 / 3.1.3(e) — оплата.** Абонементы, разовые занятия, персональные
  тренировки — это физические услуги, потребляемые вне приложения. Их **нельзя**
  продавать через In-App Purchase: только карта / эквайринг / оплата в клубе.
  Онлайн-оплата абонемента и билета на очное событие (мастер-класс) есть, но
  не через магазин: клуб подключает свой ЮKassa или Stripe (админка →
  «Настройки» → «Оплата»), участник нажимает «Оплатить онлайн» и платит на странице
  провайдера в браузере, деньги идут на счёт клуба. IAP и Play Billing для
  этого не используются и не должны. Без подключённого провайдера
  администратор, как и раньше, отмечает оплату вручную. Автоплатежи учеников
  устроены так же (раздел 10).
- **3.1.1 — цифровой контент.** Видеокурсы, продаваемые как отдельный
  цифровой продукт, внутри iOS-приложения требуют IAP. Механизмы «разблокировки»
  своими силами (коды, QR) запрещены. Варианты:
  - курсы входят в абонемент клуба и выдаются клубом, в приложении нет
    призывов купить — модель reader-приложения (3.1.3(a)); так делают BJJ
    Fanatics и MGinAction `[ВЫВОД]`;
  - отдельные курсы продаются на сайте, iOS-приложение на сайт за покупкой не
    ведёт;
  - **США:** с мая 2025 ссылки и кнопки на оплату вне приложения в
    американской витрине разрешены без entitlement; комиссия за такие покупки
    пока не установлена;
  - **ЕС (DMA):** с 1 октября 2026 единые условия — IAP 26 % (15 % малый
    бизнес), альтернативный процессинг 20 % / 10 %, ссылка на внешнее
    предложение 15 % / 10 %; выбранный вариант держится 12 месяцев.
- **3.1.3(d).** Живые занятия «один на один» могут обходиться без IAP;
  платные онлайн-трансляции «один ко многим», продаваемые в приложении, — только
  через IAP. Трансляции внутри абонемента клуба — серая зона `[ВЫВОД]`.
- **5.1.1(v) — удаление аккаунта.** Есть: Профиль → Настройки → «Удалить
  аккаунт» (код на почту аккаунта через `POST /send-auth-code`, затем
  `POST /me/delete-account` с этим кодом) и веб-страница `/legal/delete-account`.
  Удаляется весь аккаунт, не только членство в клубе. Владельцу клуба и тренеру
  группы предлагается сначала передать дела.
- **4.8 — вход.** Вход по коду на почту не требует «Sign in with Apple».
  Если добавим вход через Google или VK — понадобится равноценный вход,
  сохраняющий приватность.
- **1.2 — пользовательский контент.** Для ленты/чатов нужны фильтрация, жалобы,
  блокировка и опубликованные контакты. Жалоба на контент в приложении есть
  (`content.report`).
- **5.1.2.** Передача данных третьим лицам (в том числе сторонним AI) — только
  с явного разрешения.

### Google Play

- **Платёжная политика.** Play Billing обязателен для цифрового контента и
  **запрещён** для оплаты физических услуг — прямо названы абонементы в зал и
  билеты на мероприятия. Подписки на фитнес-, образовательный и видеоконтент —
  случай Play Billing.
- **США:** после Epic v. Google доступны альтернативный биллинг и внешние
  ссылки по программам Google, со своими комиссиями.
- **Россия:** биллинг Play приостановлен с 10 марта 2022; бесплатные
  приложения распространяются.
- **Удаление аккаунта** — в приложении и по веб-ссылке (есть, см. выше);
  ссылку `https://app.<домен>/legal/delete-account` указываем в Data safety.

### RuStore

- **§9.1:** все способы оплаты (IAP, сторонний эквайринг, свои решения, в том
  числе оплата на внешней странице) декларируются в консоли;
  незадекларированные запрещены. «Оплатить онлайн» открывает страницу ЮKassa
  или Stripe клуба — задекларировать «сторонние платёжные сервисы и эквайринг»
  до релиза (текст — `docs/store/data-safety.md`). Автоплатёж (раздел 10) —
  тот же эквайринг ЮKassa клуба, отдельного способа оплаты нет `[ВЫВОД]`.
- **§5.1:** обязательна политика конфиденциальности по 152-ФЗ —
  `https://app.<домен>/legal/privacy`.
- **§4.6:** запрет множественных публикаций одного приложения (см. раздел 1).
- Лимит публикаций: до 10 приложений в день для физлиц, для юрлиц —
  индивидуально. Аккаунт — через VK ID, юрлицо / ИП / физлицо.
- С 1 сентября 2025 RuStore обязателен к предустановке на смартфоны,
  продаваемые в России.
- **Push.** В RuStore публикуется тот же AAB/APK. Уведомления идут через Expo
  → FCM, поэтому **на телефонах без сервисов Google** (Huawei, часть
  «российских» прошивок) push не придут `[ВЫВОД]`. RuStore Push SDK потребует
  отдельной нативной зависимости и серверного канала отправки — в текущую
  сборку не входит. Пока такие ученики видят уведомления во «Входящих»
  приложения и получают письма.

### App Store и российские разработчики

- С 1 апреля 2026 Apple остановила приём платежей в App Store в России;
  покупки и продления — только с остатка баланса. Любая монетизация через IAP
  в России невозможна `[ВЫВОД]`.
- Приложения удаляются по требованию регулятора (отчёт о прозрачности Apple
  за 2025), в июне 2026 из App Store удалили приложения VK.
- Аккаунт Apple Developer для российского юрлица оформить и оплачивать
  затруднительно; публикация через иностранное юрлицо — отдельное
  юридическое решение `[ВЫВОД]`.
- **Поэтому PWA обязательна как запасной путь**: `app.<домен>` открывается в
  Safari, «На экран Домой» ставит приложение с иконкой и названием бренда
  (манифест генерирует `scripts/build-pwa.mjs`). Работает всё, кроме нативных
  push и офлайн-загрузки видео. Ссылки `/join/<код>` при отсутствии
  приложения открывают PWA.

## 5. Аккаунт для проверки магазинами

Ревьюеры не читают нашу почту, поэтому один адрес входит по фиксированному
коду. Переменные сервера (`.env.production`):

```
STORE_REVIEW_EMAIL=review@clubspace.ru
STORE_REVIEW_CODE=<6 случайных цифр: LC_ALL=C tr -dc 0-9 </dev/urandom | head -c6>
STORE_REVIEW_WORKSPACE_KEY=<ключ демо-клуба>
```

- Код проверяется при старте: оба значения или ни одного, не угадываемый
  (не `123456`, `111111` …), адрес не совпадает с `SUPER_ADMIN_EMAIL`.
  `STORE_REVIEW_WORKSPACE_KEY` без первых двух сервер тоже не примет.
- Аккаунт создаётся при первом входе фиксированным кодом — и заново, если
  ревьюер проверил «Удалить аккаунт» (send-auth-code отмечает запрос в
  `PendingSignIn`, вход фиксированным кодом создаёт аккаунт). Заводить его
  заранее не нужно. Письма на этот адрес не уходят.
- Фиксированный код открывает только аккаунт обычного ученика: администратор
  платформы, владелец клуба или тренер с этим адресом не войдёт.
- **Демо-клуб.** При каждом входе ревьюера с заданным
  `STORE_REVIEW_WORKSPACE_KEY` сервер делает его АКТИВНЫМ учеником этого клуба:
  создаёт членство, снимает «ожидает» / «заблокирован» / «приостановлен» и
  истёкший срок доступа. Если всё уже в порядке — ничего не пишет. Каждое
  изменение — событие «Аккаунт проверки магазина добавлен в демо-клуб» в
  журнале клуба и платформы; сам вход — «Вход аккаунта для проверки магазина
  приложений». Неверный ключ клуба вход не ломает, только пишет предупреждение
  в лог.
- Демо-клуб должен выглядеть живым: расписание на ближайшие недели, пара
  курсов с видео, объявления, пояса — ревьюер оценивает «полноценность»
  приложения (Apple 2.1 / 4.2).
- Не удаляйте переменные после первого релиза: каждое обновление проверяют
  заново.

Текст для App Review Information / «Доступ к приложению» в Play Console:

> Вход по коду из письма. Для проверки: e-mail `review@clubspace.ru`, нажмите
> «Получить код», введите код `<STORE_REVIEW_CODE>`. Аккаунт уже состоит в
> демо-клубе «<название>»: расписание, курсы, абонемент. Удаление аккаунта:
> Профиль → Настройки → «Удалить аккаунт».

## 6. Push-уведомления

- `expo-notifications` подключён плагином в конфиге (`app-variant.js`).
- `EAS_PROJECT_ID` → `extra.eas.projectId`: по нему Expo выдаёт push-токены.
- `GOOGLE_SERVICES_FILE` → `android.googleServicesFile`: конфигурация FCM.
  Задайте файловой переменной EAS
  (`eas env:create --type file --name GOOGLE_SERVICES_FILE …`); файл в
  репозиторий не коммитится.
- iOS: APNs-ключ загружается через `npx eas credentials` в команду Apple
  владельца приложения.
- Проверка релиза **предупреждает** (сборку не останавливает), если нет
  `EAS_PROJECT_ID` или — для Android — `GOOGLE_SERVICES_FILE`; заданный, но
  отсутствующий файл — ошибка.
- PWA: Web Push (VAPID) — плашка «Включите уведомления»; на iPhone — только
  у PWA, добавленной на экран «Домой» (iOS 16.4+) `[ВЫВОД]`.

## 7. Что меняется для текущих установок (миграция)

До этого изменения профили `production` / `store` собирали брендовое
приложение «Грэпплинг Академия» с зашитым клубом под `com.clubspace.app`.
Теперь под тем же идентификатором выходит нейтральный ClubSpace.

- **Обновление поверх старой версии работает:** тот же package, тот же slug и
  keystore EAS. После обновления у ученика на иконке «ClubSpace» вместо
  «Грэпплинг Академия».
- **Ученики клуба не теряют клуб:** членство хранится на сервере, приложение
  показывает клубы аккаунта. Заявки «на рассмотрении» остаются.
- **Новые ученики** больше не попадают в клуб автоматически при входе: им нужен
  код, ссылка или QR клуба (или приглашение по e-mail из админки). Обновите
  плакаты и сообщения в чатах клуба на ссылку `/join/<код>`.
- **Схема `grappling-academy://`** больше не регистрируется; в коде и письмах
  она не использовалась.
- **Профили `club-picker` / `club-picker-store` удалены** — это теперь
  `production` / `store`. `set-mobile-target.sh` больше не принимает
  `--club-key`.
- **Карточки магазинов:** переименуйте приложение в ClubSpace, обновите
  описание (приложение для учеников любых клубов), скриншоты и иконку.
- **Если клубу нужен прежний брендовый вид** — это брендовое приложение из его
  аккаунта с **новым** Bundle ID. Это отдельная карточка: ученики ставят её
  заново, вход тем же e-mail.
- PWA устанавливается под именем бренда сборки (для нейтральной — «ClubSpace»),
  а не «Грэпплинг Академия».

## 9. Проверка iOS на симуляторе (без окна Simulator)

В Xcode 27 нет `Simulator.app`, приложение проверяется из терминала:
`xcrun simctl` (установка, запуск, скриншоты) и `idb` (тапы, ввод, дерево
доступности).

**Сборка.** Нужна ad-hoc подпись: с `CODE_SIGNING_ALLOWED=NO` у приложения
нет keychain-entitlement, `expo-secure-store` падает с `-34018`, и вход
сбрасывается при каждом перезапуске. `EXPO_PUBLIC_*` подставляются в бандл
при сборке, без них приложение зависает на заставке.

```sh
cd apps/mobile
export EXPO_PUBLIC_API_URL=http://localhost:3000 EXPO_PUBLIC_BRAND=clubspace \
  EXPO_PUBLIC_CLUB_PICKER=true EXPO_PUBLIC_WEB_URL=http://localhost:4201
npx expo prebuild --platform ios --clean --no-install && (cd ios && pod install)
UDID=$(xcrun simctl list devices | awk -F'[()]' '/iPhone 18 Pro \(/{print $2; exit}')
xcrun simctl boot "$UDID" 2>/dev/null
(cd ios && xcodebuild -workspace ClubSpace.xcworkspace -scheme ClubSpace \
  -configuration Release -sdk iphonesimulator -destination "id=$UDID" \
  -derivedDataPath /tmp/cs-ios-dd \
  CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=)
xcrun simctl install "$UDID" /tmp/cs-ios-dd/Build/Products/Release-iphonesimulator/ClubSpace.app
xcrun simctl launch "$UDID" com.clubspace.app
xcrun simctl io "$UDID" screenshot shot.png
```

Повторная сборка после правок JS — около 20 с. Часовой пояс устройства для
проверки: `SIMCTL_CHILD_TZ=Europe/Moscow xcrun simctl launch "$UDID" com.clubspace.app`.
Ссылки: `xcrun simctl openurl "$UDID" clubspace://...`.

**Управление (idb).** `brew install idb-companion`, клиент — `uv tool install fb-idb`.
`idb_companion` ищет `SimulatorKit.framework` в
`Contents/Developer/Library/PrivateFrameworks`, а в Xcode 27 он лежит в
`Contents/SharedFrameworks`. Лечится подставным `DEVELOPER_DIR` из симлинков:

```sh
X=/Applications/Xcode.app/Contents; F=$HOME/.cache/xcfake/Xcode.app/Contents
mkdir -p $F/Developer/Library/PrivateFrameworks
for e in $X/*; do [ "${e##*/}" = Developer ] || ln -sf $e $F/; done
for e in $X/Developer/*; do [ "${e##*/}" = Library ] || ln -sf $e $F/Developer/; done
for e in $X/Developer/Library/*; do ln -sf $e $F/Developer/Library/; done
ln -sf $X/SharedFrameworks/SimulatorKit.framework $F/Developer/Library/PrivateFrameworks/
DEVELOPER_DIR=$F/Developer idb_companion --udid "$UDID" --grpc-port 10882 &
idb connect localhost 10882
idb ui describe-all          # элементы с AXLabel и координатами в точках
idb ui tap 200 600           # тап в точках (скриншот в 3× пикселях)
idb ui text "coach@academy.demo"
idb ui swipe 200 650 200 250 --duration 0.3
```

- Раскладка клавиатуры симулятора — русская: латиницу вводит только
  `xcrun simctl spawn "$UDID" defaults write -g AppleKeyboards -array "en_US@sw=QWERTY;hw=Automatic"`
  и перезапуск приложения.
- `idb ui text` теряет хвост длинной строки — вводить посимвольно и
  сверять значение поля через `describe-all`.
- Подключена аппаратная клавиатура, экранная не появляется: проверка
  «клавиатура перекрывает поле» так недоступна.
- Тапать можно только видимое: координаты из `describe-all` у элементов за
  экраном вне 0–874, сначала прокрутить свайпом.

## 10. Оплата

Ученик платит клубу онлайн мимо магазинов (раздел 4): «Оплатить онлайн»
открывает страницу ЮKassa или Stripe клуба, деньги идут на счёт клуба,
ClubSpace их не получает. Клуб подключает провайдера в админке: «Настройки» →
«Оплата».

### Автоплатежи учеников (только ЮKassa)

Ученик может сам включить автопродление абонемента при онлайн-оплате тарифа,
который клуб разрешил так продлевать. Это не подписка магазина: списания —
оплата физической услуги клуба через его ЮKassa, IAP и Play Billing не
участвуют (Apple 3.1.3(e), платёжная политика Google Play) `[ВЫВОД]`.

- **Согласие.** Переключатель «Продлевать автоматически» выключен по
  умолчанию. Под ним — условия: сумма сейчас и дальше, когда списываем, как
  отключить, и ссылка «Условия автоплатежа» на `https://app.<домен>/legal/autopay`.
  Редакция текста — `AUTOPAY_CONSENT_VERSION` на сервере
  (`apps/server/src/domains/autopay/autopay-consent.ts`); у клиента та же
  редакция — `apps/client/src/features/legal/autopay/`. Новая редакция = новый
  файл в клиенте и новая версия на сервере в одном деплое
  (`docs/legal/README.md`).
- **Отключение** — в приложении, «Мой абонемент» → «Отключить автоплатёж»
  (работает и при закончившемся доступе), или по просьбе ученика в карточке
  ученика в админке. Действует сразу, сохранённая карта больше не
  используется (376-ФЗ, ст. 16.1 ЗоЗПП).
- **Карта** хранится у ЮKassa; у нас — только её идентификатор и последние 4
  цифры. Чеки по 54-ФЗ отправляет ЮKassa, как при обычной онлайн-оплате.
- **Stripe:** автоплатежей нет, клубы со Stripe принимают только разовые
  оплаты.

Включение:

1. **Платформа.** На сервере `MEMBER_AUTOPAY_ENABLED=true` (по умолчанию
   выключено: в админке нет настройки, в приложении нет переключателя, задача
   списаний ничего не делает; отключить автоплатёж ученик может всегда).
   Перед включением — проверка на тестовом магазине ЮKassa (подключение,
   списание, отказ тестовой картой, отключение, чек) и проверка текстов
   юристом (`docs/legal/README.md`).
2. **Клуб** просит менеджера ЮKassa включить автоплатежи в своём магазине —
   без этого ЮKassa не сохранит карту, а попытка подключить автоплатёж
   покажет ошибку в «Настройки» → «Оплата» и уведомит администраторов.
3. **Клуб** добавляет условия автоплатежа в свою оферту для учеников (продавец
   абонемента — клуб).
4. **Клуб** отмечает «Автоплатежи для учеников» в «Настройки» → «Оплата»
   (видно только при подключённой ЮKassa).
5. **Клуб** отмечает «Можно продлевать автоплатежом» в нужных тарифах
   («Абонементы» → «Тарифы»; нужна галочка «Можно купить онлайн»).

Отключение настройки клуба, смена магазина или провайдера отключают все
автоплатежи клуба с уведомлением ученикам.

## 11. OTA-обновления (EAS Update)

Исправление JS после показа доходит до установленных приложений без новой
сборки и без релиза в магазинах. Приложение при каждом холодном запуске
спрашивает сервер обновлений EAS и ждёт не дольше 3 секунд: если новое
обновление успело скачаться — запускается с ним, иначе стартует с тем, что
есть, докачивает в фоне и применяет при следующем холодном запуске. Плохая
сеть запуск не держит, баннеров и вопросов «обновить?» нет. Сам
`expo-updates` откатывает только обновление, которое падает при запуске, до
первого экрана: следующий запуск идёт с предыдущим рабочим. Если ошибка
проявляется позже (после входа, на одном экране), откатывайте вручную —
«Откат» ниже.

Настройка — в `apps/mobile/src/app-variant.js` (`updates`, `runtimeVersion`),
каналы — в `eas.json`. PWA это не касается: её обновляет деплой
(`npm run build:pwa`), `expo-updates` в веб-сборку не попадает.

### Что нужно один раз (владелец)

1. `npm i -g eas-cli`, затем `eas login` под аккаунтом Expo, в котором проект.
2. `EAS_PROJECT_ID` — id проекта EAS (`eas init` или страница проекта на
   expo.dev). Задайте его в обеих средах EAS — `preview` и `production`
   (`eas env:set --name EAS_PROJECT_ID --value <id> --environment preview --environment production`;
   профиль `preview` читает среду `preview`, остальные — `production`) — **и**
   в оболочке перед командами ниже (`export EAS_PROJECT_ID=…`). Без него в
   сборке обновления выключены (`updates.enabled: false`), проверка релиза
   предупреждает.
3. Локальная копия `google-services.json` — того самого файла, что лежит в
   файловой переменной EAS `GOOGLE_SERVICES_FILE` (раздел 6). `eas update`
   файловые переменные не скачивает, а отпечаток Android считается и по
   содержимому этого файла: без него обновление не подойдёт ни одной
   Android-сборке. Храните копию вне репозитория.
4. Обновления получают только сборки, сделанные с этим изменением и с
   `EAS_PROJECT_ID`. Установленные раньше APK обновятся только переустановкой.

### Каналы

Канал записывается в сборку из профиля `eas.json`; обновление уходит в канал
и достаётся только сборкам этого канала.

| Профиль | Канал |
|---|---|
| `development` | нет — обновлений не получает |
| `preview` | `preview` |
| `production`, `store` | `production` (APK и AAB — одно приложение) |
| `branded`, `branded-store` | `branded`, в проекте EAS клуба |

Брендовое приложение клуба живёт в своём проекте EAS (свой slug, свой
`EAS_PROJECT_ID`, свой адрес обновлений), поэтому обновления ClubSpace к нему
не попадают, и наоборот. Публикуйте для клуба с `EAS_PROJECT_ID` клуба.

### Опубликовать

```bash
cd apps/mobile
export EAS_PROJECT_ID=<id проекта EAS>
export GOOGLE_SERVICES_FILE=/путь/к/google-services.json   # та же копия, что в EAS
npm run update:ota -- production "Исправлена отметка посещения"
npm run update:ota -- preview "Исправлена отметка посещения"
npm run update:ota -- branded "Исправлена отметка посещения"   # EAS_PROJECT_ID и файл клуба
```

`scripts/eas-update.mjs` запускает ровно

```bash
eas update --channel production --environment production --message "Исправлена отметка посещения"
```

(`preview` → `--channel preview --environment preview`, `branded` →
`--channel branded --environment production`) с env профиля из `eas.json`.
Флаги после сообщения передаются как есть: `--platform android`,
`--rollout-percentage 20` — постепенная раскатка на 20 % устройств.

Не запускайте `eas update` напрямую: он не читает `build.<профиль>.env` из
`eas.json`. Без этих переменных бандл ходит на запасной `localhost`, а
отпечаток (ниже) не совпадает со сборками — обновление не дойдёт. Скрипт
убирает из окружения все `EXPO_PUBLIC_*` и `APP_ASSETS_DIR` оболочки и кладёт
env профиля, как на сервере сборки; `--environment` добавляет обычные и
секретные переменные EAS (у брендового — название, Bundle ID, ключ клуба). Не
дублируйте ключи `eas.json` в переменных EAS: в `eas update` побеждают
переменные EAS, в сборке — `eas.json`.

Скрипт откажется публиковать:

- `production`/`store`, если `EXPO_PUBLIC_API_URL` или `EXPO_PUBLIC_WEB_URL`
  не https или заглушка — то же правило, что у проверки сборки;
- `production`/`store`/`branded`/`branded-store` для Android (без
  `--platform ios`), если `GOOGLE_SERVICES_FILE` не задан; заданный, но
  отсутствующий файл — ошибка для любого профиля. У `preview` файл нужен,
  только если его сборки собирались с ним.

- `eas.json` должен быть в том же состоянии, что при сборке: с адресами и
  почтой, которые записал `set-mobile-target.sh`. Не откатывайте эту правку
  перед публикацией — с заглушками бандл ходит не туда, а отпечаток не
  совпадёт.
- Публикуйте с коммита сборки плюс исправление (ветка от релизного коммита):
  в обновление уходит весь JS рабочей копии, а не только исправление.
- После публикации сверьте отпечатки сборки и обновления:
  `eas fingerprint:compare --build-id <id сборки> --update-id <id обновления>`
  (id — со страниц сборки и обновления на expo.dev). Различие в
  `google-services.json` значит, что локальная копия не та; в конфиге —
  другой env.

### Что можно и что нельзя

**Можно OTA:** код на TS/JS (экраны, логика, тексты, стили), картинки и шрифты
из бандла, `EXPO_PUBLIC_API_URL` и `EXPO_PUBLIC_SUPPORT_EMAIL` в пределах
того же профиля.

**Только новой сборкой** (для магазинов — с релизом):

- новый или обновлённый пакет с нативным кодом (`expo-*`, `react-native-*`),
  обновление Expo SDK / React Native;
- разрешения и тексты запросов (камера, галерея, уведомления);
- всё, что меняет конфиг в `app-variant.js`: название, иконка, сплэш, Bundle
  ID, схема, ссылки `/join/` (`EXPO_PUBLIC_WEB_URL`), цвет, плагины;
- `google-services.json`, APNs, подпись.

Почему `runtimeVersion` — `fingerprint`, а не `appVersion`: версия
приложения — `1.0.0` до первого релиза в магазинах, и при `appVersion` у всех
сборок была бы одна среда выполнения: обновление, которому нужен новый
нативный модуль, встало бы на старые сборки без него и падало бы при запуске.
Отпечаток считается по нативной части — конфигу приложения, нативным пакетам,
плагинам — и меняется при любом нативном изменении. Такое обновление старые
сборки просто не получат (и не сломаются); его получат новые сборки.

Правила магазинов: Google Play разрешает загружать код, который исполняется
интерпретатором (JS), Apple — интерпретируемый код, если он не меняет
назначение приложения. Исправления и небольшие доработки — да; новую
функциональность, меняющую суть приложения или обходящую проверку, OTA не
выпускаем `[ВЫВОД]`.

### Проверить, что дошло

- В приложении: «Настройки» → «О приложении» — после версии стоят первые
  8 символов id запущенного обновления («версия 1.0.0 · a1b2c3d4»). Полные id
  по платформам показывает `eas update:view <id группы>`. Пока работает бандл
  из сборки (или обновления выключены), там только версия.
- Обновление применяется со **второго** холодного запуска, если за 3 секунды
  первого не успело скачаться: закройте приложение из списка запущенных и
  откройте снова.
- История: `eas update:list --branch production`.
- Не доходит: `eas fingerprint:compare --build-id <id сборки> --update-id <id обновления>`
  покажет, чем отличается нативная часть. Обычно это другой env или нативное
  изменение — нужна новая сборка.

### Откат

- **Вернуть прежнее обновление** (id группы — из `eas update:list --branch production`):

  ```bash
  eas update:republish --group <id группы> --message "Откат: возврат к предыдущему обновлению"
  ```

- **Вернуть всех на бандл, встроенный в сборку** (runtime version — отпечаток
  из `eas update:list` или со страницы сборки):

  ```bash
  eas update:roll-back-to-embedded --channel production --runtime-version <отпечаток> --message "Откат на версию из сборки"
  ```

- Интерактивно, с выбором одного из двух: `eas update:rollback`.

Откат — тоже обновление: устройства получают его по тем же правилам (сразу
или со следующего холодного запуска). Затем исправьте и опубликуйте заново.
